# Expert Annotation Pilot — Coordinator Guide

**Project:** ML-Based Personalized Government Scheme and Subsidy Recommendation System for Farmers  
**Pilot version:** `pilot-v1.0` (git commit `7724fa7`)  
**Pilot scope:** 10 scenarios (S001–S010) × 16 eligible scheme records  

---

## Overview

This guide explains how to run the expert annotation pilot from start to finish.
The pilot produces three concrete outputs:

1. **Independent expert annotations** (JSON + CSV per expert) in `data/annotations/`
2. **Inter-rater agreement report** in `reports/pilot_agreement_report.md`
3. **Revised annotation protocol** ready for the 50–100 scenario benchmark

## Step 1 — Expert Briefing (Before Any Annotations)

Share with each expert **before** they open any annotation tool:

1. `research/dataset_research/expert_annotation_form.md` — Read Sections 1.1, 1.2, and 1.3 only.
2. The key protocol rules:
   - **Score relevance as if the scheme is perpetually available.** Do not lower a score because the portal is closed.
   - **Score 0–3 only.** Do not give half-scores or comments in place of a score.
   - **Do NOT discuss scores** with other experts before submitting.
   - **Section B items** (provisional schemes) get only qualitative text, no number.

> [!IMPORTANT]
> Each expert must complete annotations on their **own machine** in a **separate terminal session**.
> Experts must **not share session files** or discuss scores until after all experts have submitted.

---

## Step 2 — Running Each Expert's Session

Each expert runs a separate terminal session using their unique expert ID (`E1`, `E2`, `E3`):

```powershell
# From the project root directory
python scripts/run_annotation_session.py --expert-id E1 --pilot-results research/dataset_research/pilot_execution_results.json
```

Replace `E1` with `E2`, `E3`, etc. for each expert.

### Session flow

The script enforces a **two-phase protocol**:

| Phase | What happens | Availability shown? |
|:---|:---|:---:|
| **Phase 1 — Relevance** | Expert reads farmer profile, rates each scheme 0–3 | ❌ Hidden |
| **Lock confirmation** | Expert types `yes` to lock scores — cannot go back | — |
| **Phase 2 — Availability** | Availability state is revealed; expert may add a comment | ✅ Shown |
| **Section B** | Provisional schemes shown; qualitative feedback only | ✅ Shown |

After each scenario, the session is **auto-saved** as a checkpoint JSON.
If the session is interrupted, re-run the same command — it will skip already-completed scenarios.

### Session outputs

```
data/annotations/E1_annotation_session.json   ← full structured session
data/annotations/E1_annotation_session.csv    ← flat CSV for agreement analysis
```

## Step 3 — After All Experts Have Submitted

Once **all 2–3 experts** have completed their sessions:

1. Collect the `data/annotations/` directory from each expert's machine (if sessions ran on separate machines).
2. Run the agreement script:

```powershell
python scripts/compute_agreement.py \
    --annotation-dir data/annotations \
    --output-report  reports/pilot_agreement_report.md
```

This generates `reports/pilot_agreement_report.md` with:
- Krippendorff's alpha (ordinal distance, all raters)
- Pairwise quadratic weighted Cohen's kappa
- Percent agreement and adjacent agreement
- Disagreement table (all pairs with score range >= 2)
- Per-scenario summary statistics
- Section B qualitative feedback summary
- Decision gate checklist

---

## Step 4 — Review and Protocol Revision

Open `reports/pilot_agreement_report.md` and:

1. **Check the decision gate** (Section 7).
2. **Review the disagreement table** (Section 3). For each HIGH disagreement (range >= 2):
   - Was it a protocol ambiguity (fix the instructions)?
   - Was it a genuine difference in agronomic judgment (record it, proceed anyway)?
   - Was the scheme description unclear for that crop or district?
3. **Fill in Section 6** of the report with recommended protocol changes.
4. Only proceed to the 50–100 scenario benchmark when all decision gate criteria are checked.

## Agreement Metric Interpretation & Decision Gate Alignment

To ensure statistical rigor, the primary scaling decision metric is aligned with the number of participating experts:

| Number of Experts | Primary Agreement Statistic | Secondary / Supplementary Statistic | Decision Threshold for Scaling |
|:---|:---|:---|:---|
| **Exactly Two Experts (E1 & E2)** | **Quadratic Weighted Cohen's Kappa ($\kappa_w$)** | Ordinal Krippendorff's alpha ($\alpha$) | $\kappa_w \ge 0.61$ (Substantial pairwise agreement)<br>Supplementary: $\alpha \ge 0.67$ |
| **Three or More Experts (E1, E2, E3...)** | **Krippendorff's Alpha ($\alpha$) with Ordinal Distance** | Pairwise Quadratic Weighted Kappas ($\kappa_w$) | $\alpha \ge 0.67$ (Provisional scaling gate)<br>$\alpha \ge 0.80$ (Strong multi-rater benchmark) |
| **Ranked Orders (if converted)** | **Kendall's $W$ (Concordance)** | Spearman's $\rho$ | $W \ge 0.70$ (Supplementary only) |

> [!IMPORTANT]
> **Provisional Pilot Decision Rule:**
> 1. **Two-Expert Sessions (E1 & E2):** Report Quadratic Weighted Cohen's Kappa ($\kappa_w$) as the primary pairwise metric. Ordinal Krippendorff's alpha ($\alpha$) is calculated as a supplementary multi-rater continuity metric to ensure parity with the multi-rater framework.
> 2. **Three-Expert Sessions (E1, E2, E3):** Use Ordinal Krippendorff's alpha ($\alpha$) as the primary multi-rater statistic across all raters, alongside pairwise $\kappa_w$ comparisons and disagreement tables.
> 3. **Threshold Caveat:** Meeting $\kappa_w \ge 0.61$ or $\alpha \ge 0.67$ is a **provisional pilot decision gate** to evaluate whether annotation guidelines are clear enough to proceed to the 50–100 scenario expansion. It is **not** definitive proof that labels are infallible.
> 4. **Mandatory Qualitative Review:** Even when the numerical threshold is met, the coordinator must examine the **Disagreement Table (Section 3)** for all HIGH disagreements (score range $\ge 2$) and review the written qualitative justifications in **Section B** before scaling.
